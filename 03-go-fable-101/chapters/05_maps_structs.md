# 第5章 宛先台帳と荷物カルテ — map と struct

## 🚇 今日のお話

今日は事務仕事です。「伝票番号 → 荷物」を一発で引ける **宛先台帳(map)** と、
1 つの荷物の情報をひとまとめにする **荷物カルテ(struct)** を整備します。

Python でいえば `dict` と `class`(または `dataclass`)に当たりますが、
どちらも Go らしい違いと落とし穴があります。

## map — 宛先台帳

```go
// map[キーの型]値の型
fares := map[string]int{
	"north": 500,
	"south": 700,
}

fares["west"] = 650          // 追加・更新
delete(fares, "south")       // 削除
fmt.Println(len(fares))      // 2
```

### カンマ ok イディオム — 「ない」の確認

存在しないキーを引いても Python のような `KeyError` は起きず、**値のゼロ値** が返ります。

```go
fare := fares["east"]     // 0 が返る! 「運賃 0 ゴールド」と区別できない…
fare, ok := fares["east"] // 第 2 戻り値で存在を確認できる
if !ok {
	fmt.Println("未開通の行き先です")
}
```

> 🐍 **Python との違い①: KeyError がない世界**
> Python の `d["x"]` は例外、`d.get("x")` は `None` でした。Go は常に
> `d.get("x", ゼロ値)` 相当が返り、区別したければ `, ok` を受け取ります。
> **「ゼロ値が正当な値になりうる map」では `, ok` を省略してはいけません**。
> `fares["east"]` が 0 を返したとき、それは「無料」なのか「未登録」なのか——
> ここを曖昧にしたバグは型検査でも捕まりません。

### ⚠️ 落とし穴①: nil map には書き込めない

```go
var book map[string]int   // ゼロ値は nil
fmt.Println(book["x"])    // 0 — 読むのは OK
book["x"] = 1             // 💥 panic: assignment to entry in nil map
book = make(map[string]int) // 書き込む前に make(またはリテラル)で初期化
```

`var book map[string]int` と書いた時点の `book` は「ハッシュテーブルへのポインタが nil」
という状態です。テーブルの実体(値を格納するバケット)はまだどこにも確保されていません。

**読み取りが OK な理由**
`book["x"]` を読むとき、ランタイムは「ポインタが nil なら探すまでもなくゼロ値」と
即座に判定して 0 を返します。存在しないテーブルを実際に探しに行く必要がないので、
nil のままでも安全に読めます。

**書き込みが panic する理由**
`book["x"] = 1` を実行するには、値を格納するバケットをどこかに確保しなければなりません。
しかし map への代入文 `book["x"] = 1` には戻り値がなく、「新しく確保したテーブルの
場所」を呼び出し元へ伝える手段がありません。もし Go がここで勝手にテーブルを作った
としても、その新しいテーブルへのポインタを `book` 自身に書き戻す必要があり、struct の
フィールドや関数に渡された map だと「どこで暗黙の差し替えが起きたか」が追えなくなります。
そこで Go は「暗黙には確保しない、nil map への書き込みは常に panic」という単純なルール
を選びました。

> 🔍 **なぜ append と挙動が違うの?**
> nil スライスへの `append` は OK なのに、nil map への書き込みは panic——
> 一見非対称ですが、理由は「戻り値があるかどうか」です。
> `s = append(s, x)` は **新しいスライスヘッダーを戻り値として返す** ので、
> 内部で新しい配列を確保しても `s` への再代入という形で安全に反映できます。
> 一方 `book["x"] = 1` という文には戻り値がなく、「新しく確保した map を書き戻す場所」
> がありません。だから Go は書き込み時の暗黙確保を諦め、代わりに `make` を明示的に
> 呼ばせることにしたのです。**map は使う前に必ず `make` する**、と覚えてください。

> 🐍 **Python との違い**
> Python では `d = {}` と書いた瞬間に空の辞書が実体として確保されるため、この種の
> 「未初期化の落とし穴」自体が存在しません。Go がゼロ値として nil を許すのは、
> 「まだ実体を持たない」という状態をコストゼロで表現できる代わりに、書き込み前の
> 初期化をプログラマの責任にしている、というトレードオフです。

### ⚠️ 落とし穴②: 反復順序は毎回ランダム

```go
for dest, fare := range fares {
	fmt.Println(dest, fare) // 実行するたびに順番が変わる!
}
```

> 🔍 **なぜそうなっているの? — わざとランダムにしている**
> Go の map の反復順序は「不定」ではなく、ランタイムが **意図的に毎回シャッフル**
> しています。初期の Go で、たまたま安定していた順序にユーザーのコードが依存し、
> ランタイム改善で順序が変わるたびにプログラムが壊れる事故が起きました。
> そこで開発チームは「仕様外の挙動には最初から依存できなくしてしまえ」と、
> 反復開始位置を乱数で選ぶようにしたのです(Hyrum の法則:
> 「観測可能な挙動はすべて誰かに依存される」への実力行使)。
> 順序が必要なら、キーを取り出して `slices.Sort` してから回します。
>
> 🐍 Python の dict が 3.7 から **挿入順を保証** したのと真逆の決断です。
> Python は「便利だから仕様に昇格」、Go は「依存されないよう破壊」——
> 両言語の性格がいちばんよく出ている違いかもしれません。

```go
import "maps" // Go 1.23+
for _, dest := range slices.Sorted(maps.Keys(fares)) {
	fmt.Println(dest, fares[dest]) // 常にキー昇順
}
```

## struct — 荷物カルテ

複数の値をひとまとめにする型を自分で定義します。

```go
type Parcel struct {
	ID     string
	Dest   string
	Weight float64
	Fragile bool
}

p := Parcel{ID: "GX-0001", Dest: "north", Weight: 3.2, Fragile: true}
fmt.Println(p.Dest)   // north
p.Weight = 4.0        // フィールドの更新
fmt.Printf("%+v\n", p) // {ID:GX-0001 Dest:north Weight:4 Fragile:true}
```

- フィールド名を省いた `Parcel{"GX-0001", "north", 3.2, true}` も書けますが、
  フィールド追加で壊れるため **名前付きで書くのが慣習** です
- 指定しなかったフィールドは **ゼロ値** になります(コンストラクタ必須の Python と違い、
  `Parcel{}` はそれだけで完全に合法な「空のカルテ」です)

> 🐍 **Python との違い②: class ではなく「ただのデータの束」**
> Go の struct は `@dataclass` にいちばん近い存在ですが、`__init__` も継承も
> ありません。メソッドは後から外付けします(第8章)。Go には class という
> 概念自体がなく、**「データ(struct)」と「振る舞い(メソッド)」と
> 「契約(インターフェース)」を別々の部品として組み立てます**。この分解が
> Go のオブジェクト指向の全体像で、第7〜9章で 1 つずつ学びます。

### struct は値 — 代入はまるごとコピー

```go
a := Parcel{ID: "GX-0001", Weight: 3.2}
b := a          // 全フィールドのコピー!
b.Weight = 99
fmt.Println(a.Weight) // 3.2 — a は無傷
```

Python でオブジェクトを代入すると「同じ実体への参照が 2 つ」でしたが、
Go の struct 代入は **カルテの複写** です。関数に渡すときも同じくコピーが渡ります。
「元を書き換えたいのに書き換わらない」問題と、その解決策(ポインタ)は
第7章のメインテーマです。

> 🔍 **なぜ slice と挙動が違って見えるの? — 実はルールは 1 つだけ**
> 第4章で見たとおり、スライスをコピーしても「窓が2枚になるだけで裏の配列は
> 共有される」ので、`b := a` のあと `b` を書き換えると `a` 側にも影響が出ました。
> struct はまるごと独立コピーなのに、なぜスライスは共有されるのか——
> 実は Go の代入ルールは常にただ 1 つ、**「その変数自身が持つ値をコピーする」**
> です。矛盾しているように見えるのは、コピーされる「値の中身」が型ごとに違う
> からです。
>
> - `Parcel` は `ID`・`Dest`・`Weight`・`Fragile` という**データそのもの**を
>   フィールドとして抱えています。だからコピーすれば実データがまるごと複製されます。
> - スライスの実体は、実は `{ ポインタ, len, cap }` という **3 つのフィールドを
>   持つ小さな struct** です(裏の配列そのものは含みません)。だからコピーされる
>   のはこの 3 つの数値だけで、ポインタの指す先(配列)はコピーされず共有されます。
>
> つまりスライスは「特別扱いで参照渡しになる」わけではなく、**「たまたま中身が
> ポインタを含む小さな struct」だから、コピーしてもポインタの指す先までは
> 複製されない**、というだけです。`Parcel` に手を加えて内部にポインタ型の
> フィールドを持たせれば、そのフィールドだけはスライスと同じように共有されます。
> 「struct 自体を丸ごと共有したい」なら `*Parcel`(struct へのポインタ)を使う
> 選択肢もあり、これも第7章で扱います。

### 比較とマップのキー

フィールドがすべて比較可能なら、struct は `==` で比較でき、**map のキーにもなれます**。

```go
type Route struct{ From, To string }
traffic := map[Route]int{}
traffic[Route{"north", "south"}]++ // タプルをキーにする Python の dict と同じ発想
```

Python では `__eq__` を書くか `dataclass(frozen=True)` が必要だった芸当が、
Go では標準で手に入ります(スライスや map を含む struct は比較不可になる点に注意)。

## map と struct の違いと関係

ここまで map と struct を別々に見てきましたが、役割はちょうど正反対です。

| | map | struct |
|---|---|---|
| 何をまとめるか | **同じ型**の値を、キーで検索できるように集める | **異なる型**のフィールドを1つの塊にする |
| サイズ | 実行時に増減する(動的) | フィールド数はコンパイル時に固定(静的) |
| 例えるなら | 台帳(伝票番号→荷物、のような「対応表」) | カルテ(1件分の情報をまとめた「レコード」) |
| アクセス | `book["key"]` — キーで引く | `p.Weight` — フィールド名で引く |

一言で言うと、**map は「同種のものをたくさん」、struct は「異種のものを1つに」** という
真逆の集め方をしています。単独では「同種データの集合」か「1件の複合データ」しか
表現できませんが、組み合わせると「キーで引ける複合データの集合」が作れます。

**① struct を map の値にする**(データベースのテーブルに近い形)

```go
ledger := make(map[string]Parcel) // 伝票番号 → 荷物カルテ
ledger["GX-0001"] = Parcel{ID: "GX-0001", Dest: "north", Weight: 3.2}
```

**② struct を map のキーにする**(前節の `Route`)

```go
traffic := map[Route]int{}
traffic[Route{"north", "south"}]++ // from-to のペアで集計
```

つまり struct が「1件分のデータの形」を定義し、map が「その1件をキーで大量に
管理する仕組み」を提供する、という補完関係です。次の落とし穴③は、まさにこの
組み合わせ(①のパターン)特有の問題です。

## map とスライスの中の struct — 落とし穴③

```go
parcels := map[string]Parcel{"GX-0001": {Weight: 3.2}}
parcels["GX-0001"].Weight = 4.0 // ❌ コンパイルエラー!
// cannot assign to struct field parcels["GX-0001"].Weight in map
```

「あれ、冒頭では `fares["west"] = 650` って map に直接書き込めていたのに、
今度はダメなの?」と思うかもしれません。両者の分かれ目は
**値を丸ごと差し替えるか、値の一部だけを書き換えるか** です。

| 書き方 | やっていること | 結果 |
|---|---|---|
| `fares["west"] = 650` | キーに対応する値を**丸ごと新しい値に差し替える** | ✅ OK |
| `parcels["GX-0001"] = p` | キーに対応する struct を**丸ごと差し替える** | ✅ OK |
| `parcels["GX-0001"].Weight = 4.0` | struct の中の `Weight` フィールド**だけ**を書き換える | ❌ NG |

「map から取り出した struct はコピーだから、書き換えても無駄になるだけ」——
そう思うかもしれませんが、実際には Go は無駄な代入を **実行前にコンパイルエラー**
で止めてくれます。これは「struct だから」ではなく、**アドレス指定可能
(addressable)かどうか** という、Go 全体に共通するもっと一般的なルールのためです。

**なぜ「丸ごと差し替え」はOKで「部分書き換え」はNGなのか**
`fares["west"] = 650` は「キー `"west"` にこの値を置け」という **1回きりの書き込み
命令** です。Go コンパイラはこれを `mapassign` という専用のランタイム関数呼び出しに
変換し、①ハッシュ値を計算 → ②バケットの場所を特定 → ③そこへ値をまるごとコピー、
という一連の処理をその場で完結させます。呼び出し元が「アドレスを保持し続ける」
必要は一切ありません。

一方 `parcels["GX-0001"].Weight = 4.0` は、内部的には
`(&parcels["GX-0001"]).Weight = 4.0` という **2段階の操作** です。
①「map 内の struct のアドレスを取る」→ ②「そのアドレス経由で `.Weight` だけを
書き換える」。①のアドレスを②まで保持し続ける必要がありますが、map の内部は
ハッシュテーブルで、要素の追加・削除のたびにバケットが再配置(rehash)される
可能性があります。今アドレスを取れても、次の瞬間には同じキーのデータが別の場所へ
移っているかもしれません。**安定したアドレスを保証できない**ので、Go は
「map の要素そのものへのアドレス取得」を①の時点で仕様レベルで禁止しています。

> 🔍 **そもそもハッシュテーブルとは**
> 配列は「添字(0, 1, 2...)」で直接アクセスできますが、ハッシュテーブルは
> **キー(文字列など)をハッシュ関数で数値に変換し、その数値を添字として使う配列**
> です。
> ```
> "north" → ハッシュ関数 → 12345 → 配列の (12345 % 配列サイズ) 番目に格納
> "south" → ハッシュ関数 → 67890 → 配列の (67890 % 配列サイズ) 番目に格納
> ```
> 同じキーなら常に同じ数値になるので、検索するときも同じ計算をすれば一発で
> 場所が分かります。先頭から順に比較する必要がないので、要素数が増えても
> `book["north"]` はほぼ一定時間(`O(1)`)で引けます。
>
> ただし配列のサイズは有限なので、キーが増えるほど**衝突**(違うキーが同じ場所を
> 計算してしまうこと)が増え、検索が遅くなっていきます。そこで要素数が一定を
> 超えると、ランタイムは内部の配列をより大きく作り直し、**全要素をハッシュ値から
> 計算し直して新しい配列へ移し替えます**。これが本文中の「バケットの再配置
> (rehash)」の正体です。あるキーのデータが物理的に別の配列・別の位置へ
> 引っ越すことがあるため、Go は map の要素へのアドレスを安全に渡せないように
> しています。
>
> 一方スライスは「添字→データ」が「先頭アドレス + 添字 × 要素サイズ」という
> 単純な計算だけで済み、再配置という概念自体がありません。これが次に見る
> 「スライスなら通る理由」の根っこにある違いです。

> 🔍 **同じ書き方でもスライスなら通る理由**
> 「struct を要素に持つコレクション」という点は同じでも、スライスなら結果が変わります。
> ```go
> ps := []Parcel{{Weight: 3.2}}
> ps[0].Weight = 4.0 // ✅ こちらはコンパイルが通る!
> ```
> スライスの要素は裏の配列上に連続して並んでいて、`&ps[0]` は
> 「先頭アドレス + インデックス × 要素サイズ」という単純な計算で求まる
> **安定したアドレス** です(要素数が変わらない限りどこにも動きません)。
> だから `ps[i].Field` へ直接代入できます。map はハッシュテーブルという
> 構造上そもそも「要素の固定アドレス」という概念がないため、この特典を
> 受けられません。**違いの正体は「struct かどうか」ではなく「アドレスが
> 取れる(addressable)かどうか」** という一段抽象度の高いルールです。

**直し方は3ステップ**——取り出す・直す・戻す、を分けて書けば済みます。

```go
p := parcels["GX-0001"] // ① 値をコピーして取り出す(p は普通の変数 → アドレスが取れる)
p.Weight = 4.0          // ② コピーの方を直す
parcels["GX-0001"] = p  // ③ 直したコピーで丸ごと上書きする(= 丸ごと差し替えなので OK)
```

もう1つの解決策は、最初から `map[string]*Parcel`(struct へのポインタを値にする map)
にしておくことです。map から取り出されるのは「ポインタという値のコピー」ですが、
指し示す先の struct 本体は1つだけなので、`parcels["GX-0001"].Weight = 4.0` が
そのまま書けるようになります。ただしポインタを扱う分「誰が元の値を書き換えられるか」
という設計判断が新たに必要になり、これは第7章のテーマです。

## 🚇 完成コード: `express/day5/main.go`

```go
// Gopher Express — 台帳とカルテの整備
package main

import (
	"fmt"
	"maps"
	"slices"
)

type Parcel struct {
	ID      string
	Dest    string
	Weight  float64
	Fragile bool
}

func main() {
	// 伝票番号 → 荷物カルテ の台帳
	ledger := make(map[string]Parcel)
	ledger["GX-0001"] = Parcel{ID: "GX-0001", Dest: "north", Weight: 3.2, Fragile: true}
	ledger["GX-0002"] = Parcel{ID: "GX-0002", Dest: "south", Weight: 42.0}
	ledger["GX-0003"] = Parcel{ID: "GX-0003", Dest: "north", Weight: 0.4}

	// 問い合わせ対応
	if p, ok := ledger["GX-0002"]; ok {
		fmt.Printf("照会: %+v\n", p)
	}

	// 日報は伝票番号順で(map の順序は当てにしない!)
	fmt.Println("--- 本日の台帳 ---")
	for _, id := range slices.Sorted(maps.Keys(ledger)) {
		p := ledger[id]
		mark := ""
		if p.Fragile {
			mark = " ⚠️割れ物"
		}
		fmt.Printf("%s: %s 行き %.1fkg%s\n", id, p.Dest, p.Weight, mark)
	}
}
```
